# Secondary Category Main-Template Corrections Design

## Goal

Complete SHOP-177 and SHOP-178 Secondary Category behavior on the current `task-177` architecture while preserving its team-approved per-module Contracts boundary, unified database, and back-office GraphQL API.

## Architectural baseline

Secondary Category remains an independent merchandising taxonomy. It has no relationship to primary Catalog categories; products may belong to multiple secondary categories. The module follows the branch's established structure: framework-free `Contracts` and `Application`, EF-backed `Adapter.Outbound`, read-only `QueryApplication`, inbound REST/GraphQL adapters, and `Installer` composition.

The current `task-177` branch is authoritative for this implementation:

- Production persistence uses the single `EwaysVNextDbContext`.
- Secondary Category retains its existing `ISecondaryCategoryUnitOfWork` and serializable execution-strategy transaction convention; this task does not introduce a new transaction abstraction.
- Aggregate identifiers are generated by `IIdGenerator` in Application and mapped with `ValueGeneratedNever()`.
- Secondary Category's DTOs remain in its independent `.Contracts` project. References to the obsolete centralized `BuildingBlocks.Contracts` project are removed from this module.
- Existing internal domain events are retained; no event is introduced for cross-module orchestration.

The work aligns only the remaining Secondary Category deviations with the architecture established in the current `task-177` branch. It does not redesign other modules or perform a repository-wide migration.

## Catalog contract boundary

A minimal framework-independent `Catalog.Contracts` project exposes only the product-availability capability required by Secondary Category. It has no reference to Catalog Domain, Application, adapters, persistence, the unified DbContext, or any other implementation project.

Catalog Application references `Catalog.Contracts`, and its existing product application service implements the public availability contract. Secondary Category Application continues to own `ICatalogProductLookup`; its outbound adapter implements that port by calling the Catalog contract. Therefore, the actual project dependency is `SecondaryCategory.Adapter.Outbound -> Catalog.Contracts`, not `SecondaryCategory.Application -> Catalog.Application`, and no Catalog repository, DbContext, UnitOfWork, or general-purpose `IProductService` is exposed.

Catalog DI registers `ProductService` once per scope and maps both Catalog's internal interface and the public product-availability Contract to that same scoped instance.

This is the only additional module Contract introduced by this work. It is a focused boundary correction, not a repository-wide Contracts migration.

## Hierarchy validation

The acceptance criteria define roots as level one and require a maximum hierarchy depth of five levels for both creation and subtree moves. Creating a child below a level-five parent therefore fails. Moving a subtree fails when the proposed parent depth plus the moving subtree height would place the moved root or any descendant below level five.

Cycle and depth checks must not query once per ancestor or descendant. Each create or move validation uses one hierarchy round-trip that returns enough topology to determine the proposed parent depth, detect whether the proposed parent is inside the moving subtree, and calculate the complete subtree height. The SQL Server adapter uses a recursive hierarchy query with an explicit visited path so corrupt cycles terminate safely. The InMemory fallback materializes the required hierarchy rows with one asynchronous query and performs traversal with a visited-ID set. Both paths observe the caller's cancellation token, including during in-memory traversal.

Hierarchy topology includes soft-deleted rows: a deleted intermediate node remains traversable for cycle, depth, and descendant calculations. Failures remain application `Result` values with stable codes. Cycle failures use `SECONDARY_CATEGORY_CYCLE`; depth failures use `SECONDARY_CATEGORY_DEPTH_EXCEEDED`. A level-six create reports that a secondary category cannot be created below level five; a rejected move reports that the move would place a category below level five.

## Atomic hierarchy deactivation

Deactivation affects the requested non-deleted category and every eligible non-deleted descendant. All subtree aggregates, including deleted traversal nodes, are loaded as tracked entities in one cycle-safe hierarchy query. The service skips mutation of deleted nodes but continues traversal through them and calls `SecondaryCategory.Deactivate(now)` on every eligible non-deleted node. One `ISecondaryCategoryUnitOfWork.SaveChangesAsync` persists the operation inside the module's existing serializable execution-strategy transaction boundary.

This deliberately does not use `ExecuteUpdateAsync`: direct bulk DML would bypass aggregate behavior, domain-event capture, and registered persistence interceptors. The selected approach avoids the existing N-query/N-save behavior while retaining the architecture's write pipeline. The caller's cancellation token is passed through the serializable executor, hierarchy query, traversal, and single save. Every changed row receives the same `UpdatedAt` value.

Activation continues to load and activate only the requested category. It never changes descendants. Reactivation remains blocked while the parent is inactive.

## EF Core relationship and identifiers

`SecondaryCategory` exposes explicit `Parent` and read-only `Children` navigations backed by a private collection. EF configures `ParentId` as the optional foreign key and uses `DeleteBehavior.Restrict`, matching the soft-delete-only lifecycle and preventing physical cascade deletion.

`SecondaryCategory.Create` accepts a generated `long id`. `SecondaryCategoryService` obtains the ID from `IIdGenerator`, constructs the aggregate, saves once, and returns that same ID only after persistence succeeds. EF maps the key with `ValueGeneratedNever()`. The unified migration and model snapshot are updated accordingly.

## GraphQL API

Existing create, activate, and deactivate mutations remain thin authorized adapters over `ISecondaryCategoryService`. Create returns the persisted Snowflake ID.

The admin query port gains one hierarchy operation returning tree DTOs owned solely by `SecondaryCategory.Contracts`; `QueryApplication` must not define duplicate transport DTOs. `QueryApplication` retrieves all required category projections in one cancellation-aware, no-tracking query and assembles parent/child nodes in memory with cycle-safe visited-ID traversal, avoiding resolver-per-node database access and N+1 queries. Admin hierarchy data includes inactive and soft-deleted records so back-office users can manage the complete taxonomy.

Application/domain failures are converted to Hot Chocolate errors at the final GraphQL boundary. Authorized Hot Chocolate executor tests verify `message`, `code`, and `httpStatus` for not-found, invalid parent, inactive parent, deleted category, cycle, depth exceeded, slug conflict, concurrency conflict, and persistence conflict outcomes. Executor tests also prove create returns the persisted Snowflake ID `912345678901L`, activate/deactivate dispatch correctly, unauthorized hierarchy access is rejected, and the hierarchy includes inactive and deleted nodes.

## Verification and commits

Work is delivered in separately verified commits:

1. Correct the minimal Catalog Contract boundary and remove Secondary Category's obsolete centralized Contract references.
2. Replace sequential descendant lookup and enforce the required five-level depth.
3. Implement atomic hierarchy deactivation and activation isolation.
4. Configure explicit self-reference navigation and Snowflake-generated IDs.
5. Add GraphQL hierarchy retrieval and executor-level error/ID coverage.
6. Run architecture, unit, persistence-contract, integration, restore, and full-build checks; environment-only failures are reported separately.

Each behavior change follows red-green-refactor: add a focused failing test, confirm the expected failure, implement the minimum change, rerun the focused and affected suites, then commit the checkpoint.
